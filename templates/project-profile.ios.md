# Project Profile — __PROJECT_NAME__

The single source of truth for everything stack- and repo-specific. Every agent reads this before running build, test, or validation commands. Keep it current — agents trust it over their own assumptions.

## Platform & languages

- iOS 18+, iPhone only
- Swift 6, SwiftUI
- Xcode project generated by XcodeGen from `project.yml` (`.xcodeproj` is gitignored — never edit it by hand; edit `project.yml` and re-run `xcodegen generate`)

## Validation sequence

Run in order; all must pass ("all checks pass" means exactly this list):

```bash
xcodegen generate
xcodebuild build -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -quiet
xcodebuild test -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -quiet
swiftlint --strict   # skip if swiftlint is not installed; note the skip in your report
```

## Test frameworks

- **Unit:** XCTest (`Tests/`)
- **UI / E2E harness:** XCUITest on the iOS Simulator (`UITests/`) — this is the harness the Test agent's phase-validation mode runs over the phase's user-facing flows
- **Smoke suite convention:** keep one fast XCUITest smoke plan (launch → primary flow → key assertion) under ~2 minutes; it runs in every component validation. Deeper flow suites run at phase validation.
- **Accessibility identifiers:** every interactive SwiftUI element gets a stable `.accessibilityIdentifier` — XCUITest and the simulator MCP tools depend on them.

## Agent tooling

- **XcodeBuildMCP** (configured in this repo's `.mcp.json`) is the primary tool for building, running, testing, and interacting with the simulator (tap/swipe/type/screenshot, log capture). Prefer its tools over raw shell `xcodebuild` for interactive develop-and-verify loops.
- **ios-simulator MCP** (also in `.mcp.json`) is the fallback for UI interaction if an XcodeBuildMCP tool misbehaves.
- The **Validation sequence** above remains the arbiter of "all checks pass" — run it as written (via XcodeBuildMCP test tools or shell).
- **Reuse the booted simulator; never boot duplicates.**

## Human validation channel

**TestFlight on a physical device.** At the end of each phase, after the automated phase validation passes: request approval under **Required actions (human)**, then run the Distribution command below (agent-run once approved), and list "install the TestFlight build and validate the phase's flows on device" as the remaining human task. Automated simulator results do not substitute for this gate.

## Distribution

`fastlane beta` (defined in `fastlane/Fastfile`) regenerates the project, stamps the build number from the git commit count, builds and signs (Xcode-automatic, `-allowProvisioningUpdates`), and uploads to TestFlight using the App Store Connect API key configured in `fastlane/.env`. **Agent-run only after explicit approval at the phase gate — never unprompted.** Processing takes ~5–30 min; the TestFlight push notification signals the build is installable. `fastlane test` is an alternative wrapper for the simulator test run.

## Test & coverage policy

Essential tests proving the primary paths. Coverage is **not measured** — do not add coverage flags or report coverage gaps as findings.

## Run instructions

```bash
xcodegen generate && open __PROJECT_NAME__.xcodeproj    # develop in Xcode
xcrun simctl boot '__IOS_SIMULATOR__'                    # boot the simulator headlessly
xcodebuild -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' build
```

Secrets and configuration live in root-level `.env.local` (copied from `.env.example`; gitignored). For iOS, prefer injecting values via xcconfig/Info.plist at build time rather than reading `.env.local` at runtime.

## Git workflow contract

- `main` is protected — never commit to or merge `main` directly.
- One branch per phase: `phase-<X>`. Components are committed to the phase branch, one commit per component (`feat(phase-X): Component X.Y — <name>`).
- The phase branch merges to `main` only after `docs/phase-X-test-report.md` is PASS **and** the human has approved (merge request goes under Required actions).
- Standalone fixes outside a phase: short-lived branch + PR.

## External services & human-task inventory

Feeds Component X.1 (human setup) of each phase:

- Apple Developer Program membership (account holder action)
- Signing & provisioning (Xcode-managed signing; team ID configured in `project.yml`; Apple ID added in Xcode → Settings → Accounts)
- **App Store Connect API key** (role: App Manager) — the `.p8` lives ONLY in `~/.appstoreconnect/private_keys/`; Key ID / Issuer ID / path go in `fastlane/.env` (gitignored). Never commit the `.p8`.
- App Store Connect app record + bundle ID registration (`__BUNDLE_ID__`) — deferred to the first TestFlight window (needs the final app name; ~2 min by hand, faster than automating)
- TestFlight internal testing group (for the per-phase human validation channel; internal builds skip Beta App Review)
- App Store review — treat as an external dependency with lead time in the phase plan
- Machine/account setup walkthrough: `supporting-files/ios-setup-runbook.md`
