# Project Profile — __PROJECT_NAME__

The single source of truth for everything stack- and repo-specific. Every agent reads this before running build, test, or validation commands. Keep it current — agents trust it over their own assumptions.

## Platform & languages

- iOS 18+, iPhone only

## Validation tiers

Use the smallest tier that proves the current change. A role change is not a reason to repeat a passing command. Every component gate records exact commands, result, duration, and a scoped fingerprint command formed by appending its explicit source/test/config paths after `python3 scripts/worktree-fingerprint.py --`; the phase gate uses the unscoped command. Evidence is reusable only while its scope is unchanged.

Existing projects must migrate any legacy single `Validation sequence` in `docs/project-profile.md` to these three tiers. Template sync deliberately does not overwrite that project-owned file.

### Tier 1 — Targeted inner loop

Owned by Implement while coding. Run focused build/test/lint checks through XcodeBuildMCP; these are rapid feedback, not a completion gate except for an explicitly `fast`, non-runtime setup/documentation component. The executable raw fallback has no unresolved placeholders:

```bash
xcodegen generate  # only when project.yml changed
xcodebuild build -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -quiet
swiftlint --strict  # skip if unavailable; record the skip
```

### Tier 2 — Component gate

Run exactly once for the component's final fingerprint. Implement owns this gate in the `fast` and `review` assurance lanes. Independent Test owns it in the `test` and `full` lanes; Implement does not run it first. Review consumes unchanged-tree evidence without rerunning it. The phase-final validation component uses the `phase-gate` lane instead of Tier 2.

```bash
xcodegen generate
xcodebuild build -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -quiet
xcodebuild test -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -only-testing:__PROJECT_NAME__Tests -quiet
xcodebuild test -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -only-testing:__PROJECT_NAME__UITests/LaunchUITests -quiet
swiftlint --strict   # skip if unavailable; record the skip
```

Replace `LaunchUITests` with the repository's stable smoke suite if it is renamed. The smoke suite covers launch, the component's primary affected flow, and a key assertion; deeper UI flows belong to Tier 3.

### Tier 3 — Phase gate

Mandatory and owned by independent Test after all non-final components are committed and the `phase-gate` component has passed aggregate static Review. Run the cumulative unit, integration, and XCUITest suites plus the phase plan's named UI and critical-backend Validation Targets:

```bash
xcodegen generate
xcodebuild build -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -quiet
xcodebuild test -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' -quiet
swiftlint --strict   # skip if unavailable; record the skip
```

### Risk routing and shared resources

- Assign exactly one assurance lane during handoff: `fast` (Implement gate + Implement commit), `test` (Test gate + Implement commit), `review` (Implement gate + Review commit), `full` (Test gate + Review commit), or `phase-gate` (aggregate Review + mandatory Test Phase X; Review commits).
- Test is triggered by UI/OS/external behaviour not fully proven by deterministic component tests, cross-component or persistence round trips, primary-path mocks/fakes, permissions/privacy/security, migrations or destructive state, concurrency/background execution, first use of a runtime/integration pattern, or regression-prone observable behaviour. Review is triggered by shared/core/app-entry/build/config/signing files, new or changed public API/schema/protocol/cross-component contracts, security/privacy authorization, a spec deviation or ADR, an open Technical Validation risk, an ownership exception, broad scope, or incomplete/contradictory evidence. Use `full` when both sets trigger or any critical signal appears; otherwise use `test`, `review`, or `fast`. The phase-final validation component always uses `phase-gate`.
- Code authoring is serialized by default on the phase branch, with one active component-delivery engagement at a time through its gate and commit. Parallel component authors are forbidden unless this profile is deliberately extended with a complete component-branch/worktree integration protocol (branch names, base synchronization, serialized integration order, conflict owner, and post-integration evidence rule). The Lead Coordinator serializes all simulator operations behind one validation lease. Reuse the booted `__IOS_SIMULATOR__`; never boot a duplicate. It also serializes Git-index mutation, commits, and pushes. In solo/direct mode, the acting agent verifies exclusive simulator/index ownership and self-holds the guard.
- Once the phase/component spec is approved, agents do not pause for per-component plan approval. Pause only for a material spec change, conscious descope, new external authority, or a project-profile human gate.

## Test frameworks

- **Unit:** XCTest (`Tests/`)
- **UI / E2E harness:** XCUITest on the iOS Simulator (`UITests/`) — this is the harness the Test agent's phase-validation mode runs over the phase's user-facing flows
- **Smoke suite convention:** keep one fast XCUITest smoke plan (launch → primary flow → key assertion) under ~2 minutes; Tier 2 runs it once per component fingerprint. Deeper flow suites run at Tier 3.
- **Accessibility identifiers:** every interactive SwiftUI element gets a stable `.accessibilityIdentifier` — XCUITest and the simulator MCP tools depend on them.

## Agent tooling

- **XcodeBuildMCP** (configured in this repo's `.mcp.json`) is the primary tool for building, running, testing, and interacting with the simulator (tap/swipe/type/screenshot, log capture). Prefer its tools over raw shell `xcodebuild` for interactive develop-and-verify loops.
- **ios-simulator MCP** (also in `.mcp.json`) is the fallback for UI interaction if an XcodeBuildMCP tool misbehaves.
- The **Validation tiers** above are authoritative. Use XcodeBuildMCP or their shell equivalents, preserve the tier boundary, and do not repeat unchanged-tree evidence.
- **Reuse the booted simulator; never boot duplicates.**

## Human validation channel

**TestFlight on a physical device.** At the end of each phase, after the automated phase validation passes: request approval under **Required actions (human)**, then run the Distribution command below (agent-run once approved), and list "install the TestFlight build and validate the phase's flows on device" as the remaining human task. Automated simulator results do not substitute for this gate.

## Distribution

`fastlane beta` (defined in `fastlane/Fastfile`) regenerates the project, stamps the build number from the git commit count, builds and signs (Xcode-automatic, `-allowProvisioningUpdates`), and uploads to TestFlight using the App Store Connect API key configured in `fastlane/.env`. **Agent-run only after explicit approval at the phase gate — never unprompted.** Processing takes ~5–30 min; the TestFlight push notification signals the build is installable. `fastlane test` is an alternative wrapper for the simulator test run.

## Run instructions

```bash

xcrun simctl boot '__IOS_SIMULATOR__'                    # boot the simulator headlessly
xcodebuild -scheme __PROJECT_NAME__ -destination 'platform=iOS Simulator,name=__IOS_SIMULATOR__' build
```

Secrets and configuration live in root-level `.env.local` (copied from `.env.example`; gitignored). For iOS, prefer injecting values via xcconfig/Info.plist at build time rather than reading `.env.local` at runtime.

## Git workflow contract

- `main` is protected — never commit to or merge `main` directly.
- One branch per phase: `phase-[X]`. Components are serialized and committed to the phase branch, one commit per component (`feat(phase-X): Component X.Y — [name]`).
- The phase branch merges to `main` only after `docs/phase-X-test-report.md` is PASS **and** the human has approved (merge request goes under Required actions).
- Standalone fixes outside a phase: short-lived branch + PR.

## External services & human-task inventory

Feeds Component X.1 (human setup) of each phase:

- Apple Developer Program membership (account holder action)
- Signing & provisioning (Xcode-managed signing; team ID configured in `project.yml`; Apple ID added in Xcode → Settings → Accounts)
- **App Store Connect API key** (role: App Manager) — the `.p8` lives ONLY in `~/.appstoreconnect/private_keys/`; Key ID / Issuer ID / path go in `fastlane/.env` (gitignored). Never commit the `.p8`.
- App Store Connect app record + bundle ID registration (`__BUNDLE_ID__`) — deferred to the first TestFlight window (needs the final app name; ~2 min by hand, faster than automating)
- TestFlight internal testing group (for the per-phase human validation channel; internal builds skip Beta App Review)
- App Store review — treat as an external dependency with lead time in the phase plan
- Machine/account setup walkthrough: `supporting-files/ios-setup-runbook.md`
